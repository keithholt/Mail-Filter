# Store build workflow

This Xcode project builds the existing filtering engine as one sandboxed host and embedded MailKit extension. Its app targets and Store archives exclude the uninstaller, PATH component and CLI. A separate Local Installer helper target runs `MacApp/package.sh local`, which builds and packages the direct app, uninstaller and engineering CLI.

## Build inside Xcode without signing

1. Open `MacApp/Store/Mail-Filter.xcodeproj` in Xcode.
2. Select the **Mail-Filter Build Check** scheme and **My Mac** destination in the toolbar.
3. Choose **Product > Build** (Command-B). This compiles the app, embeds its MailKit extension, and copies the prompts, icon and privacy manifests. No Apple Account, team or certificates are required.
4. Use the Issue navigator (Command-5) to inspect compiler errors. The **Build Configuration** navigator group contains the configuration files and this guide.

The `BuildCheck` configuration inherits the development identifiers, disables code signing for both targets, and ignores a locally configured signing team. Its scheme has no runnable executable and disables archive/profile builds. Use it for compilation only: signed development is required to qualify sandbox permissions and App Group sharing. Building does not install the app, activate its Mail extension, or change the working filter's settings. Xcode records app build products with Launch Services, so these products use the isolated development identifiers.

The **Mail-Filter** scheme remains available for signed development (Run) and Store distribution (Archive). Changing schemes does not require editing build settings. Native checks continue through `MacApp/test.sh`; the engineering CLI remains a Swift package at the repository root. Word documentation is regenerated by the shell build entry points described below.

Xcode may also show an automatic **MailFilterExtension** scheme. This is a component development/debugging entry point that uses development signing; it requires a configured team. The host app and Local Installer builds already include the extension. For an unsigned compile of both components, choose **Mail-Filter Build Check**. Open this `.xcodeproj` file explicitly; opening the repository folder instead loads the CLI's Swift package and exposes a different scheme list.

Expand **Repository** in the Project navigator to browse the source, tests, scripts, prompts and docs in their repository folders. File labels use their basenames; the references still point to the same files under `Documents/GitHub/Mail-Filter`. **Build Configuration** provides convenient access to the signing/build configuration files. Navigation does not determine target membership: the generator's explicit source/resource lists do. After adding public files, regenerate the project; Git's inventory omits ignored private settings and build outputs.

Development payload checks allow Xcode's named debug/preview libraries. Production Store payloads still require only the release executable in each bundle's executable directory.

## Create the local installer inside Xcode

1. Select the **Mail-Filter Local Installer** scheme in the same project.
2. Choose **Product > Build** (Command-B).
3. Wait for **Build Succeeded**. The helper target runs the maintained local packaging script: it regenerates Word docs, rebuilds the direct app and its embedded extension, adds the CLI and uninstaller, applies ad hoc local signing, creates the package and runs bundle/package verification.
4. Open `outputs/Mail-Filter Installer.pkg` in the repository when you intend to install it. The packager also maintains a Desktop shortcut to that package. A conflicting unrelated Desktop item is left untouched.

This action creates the package only. It does not launch Installer, install or uninstall apps, change the PATH or filtering settings, or enable extensions. The package is a local test build; App Store or notarized public distribution remains a separate workflow. Each explicit build of this helper target reruns packaging. Select **Mail-Filter Build Check** again for faster compiler-only work.

The helper target alone disables Xcode's script sandbox because the maintained packager writes repository outputs and the Desktop shortcut. It has no dependency on the sandboxed Store targets and does not change their signing, entitlements or script sandbox settings.

## Shell build checks

Run from the repository root:

```sh
./MacApp/test.sh
./MacApp/store-build.sh check
```

`check` regenerates Word documentation and produces an **unsigned** archive at `.build/store-unsigned.xcarchive`. It compiles the Store configuration with isolated development identifiers because Xcode records build products with Launch Services. This neither installs the app nor enables its extension. Do not open this unsigned product or use it for live filtering. Successful compilation does not establish sandbox permissions, App Group access or App Review acceptance.

The project files are available for normal Xcode use. `generate-project.py` deterministically regenerates them after changing source lists; `--check` detects drift. All three configurations compile shared sources with `APP_STORE`, which excludes the system-log subprocess collector and hides direct-installer controls. Local builds retain their engineering tools.

| Configuration | Bundle and group |
|---|---|
| BuildCheck (unsigned compilation only) | Development identifiers below; signing disabled |
| Development | `org.mail-filter.development` and `group.org.mail-filter.development.shared` |
| Store | `org.mail-filter.app` and `group.org.mail-filter.shared` |

Confirm identifier availability after enrollment. Register the host, its `.extension` identifier and the matching group for each configuration. Enable App Sandbox and the same group for both targets. There is no fallback to the installed local app's storage when a group is unavailable. The host additionally requests user-selected read/write file access and a Mail-targeted Apple Events exception. The extension has neither that exception nor the local-development filesystem exception.

## Signed builds after developer access is available

1. Copy `Signing.example.xcconfig` to `Signing.local.xcconfig` in this directory and set `DEVELOPMENT_TEAM` to the actual ten-character paid developer Team ID. The local file is ignored by Git and applies to both signed targets/configurations. Open `Mail-Filter.xcodeproj`, select the **Mail-Filter** scheme, and confirm the resolved team under Signing & Capabilities for both targets. Keep automatic signing enabled and allow Xcode to create/download the matching development profiles. Avoid writing team overrides into the generated project; they would be lost on regeneration. Review the entitlements rather than adding broad exceptions to resolve an error.
2. Set `MAIL_FILTER_TEAM_ID` to the actual ten-character team identifier in Terminal, then run `./MacApp/store-build.sh development`. This creates a separately identified sandboxed development app. Qualify its storage and file panels before enabling its extension. Use an isolated macOS user or designated test setup; never enable both filtering extensions against the same working inbox.
3. Import a private setup export or explicitly select the old data folder containing both `settings.json` and `junk-protection.json`. The import preserves pause/preview, inventory, aliases and selections, merges recovery protection, and waits for **Confirm Imported Setup**. A private `migration-backup.json` holds the previous destination setup. Keep original files and exports until qualification succeeds. A legacy folder missing protection is rejected; export a complete setup from the updated direct app instead.
4. Test full Mail account discovery and selected-message source access, including permission denial, restarts and user-selected export. The desktop count probe established only partial automation feasibility. The manual address and `.eml` paths must remain usable without automation.
5. Configure distribution signing/profiles in Xcode and run `./MacApp/store-build.sh archive`. It preserves any existing archive by refusing to overwrite `outputs/store/Mail-Filter.xcarchive`. The verifier checks signed capabilities, provisioned groups, privacy manifests and payload exclusions. Complete isolated Mail action/update tests before upload.
6. Run `./MacApp/store-build.sh export` to create a local App Store Connect export under `outputs/store/export`, or validate and distribute through Xcode Organizer. Export does not upload. Submission and publication remain explicit publisher actions.

The privacy manifest declares elapsed-time measurement and metadata access within authorized storage and user-selected files. Its current reasons are `35F9.1`, `C617.1` and `3B52.1`. Re-audit them when shipped API use changes. The app has no telemetry or email-upload service. App Store privacy answers must also consider any support process the publisher later adopts.

The Store support path uses bounded private activity and JSON-lines history, with Save Report for user-selected export. It does not invoke `/usr/bin/log`. File history is supplementary: write failures must not change classification or persistent recovery protection. The direct developer build may additionally collect its own unified logs.

See the deployment plan and review preparation in `docs/`. The account, signed runtime, clean-install UI, actual Mail actions, TestFlight and App Review gates are still outstanding.
