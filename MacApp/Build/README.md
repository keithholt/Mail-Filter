# Native build configuration

Open `Mail-Filter.xcodeproj` at the repository root. `MacApp/generate-project.py` defines all native targets and generates the checked-in project and shared schemes. Source files remain in their existing repository folders.

Use **Mail-Filter Dev** for signed sandboxed development beside an installed Store app, **Mail-Filter Store** for Store archives, **Mail-Filter Dev Installer** for the separate Dev package, **Mail-Filter Local** and **Mail-Filter Local Installer** for the legacy direct distribution, **Mail-Filter Build Check** for unsigned sandboxed compilation, or **mail-filter CLI** for engineering work. Build the host to automatically build and embed its MailKit extension.

The Dev configuration displays **Mail-Filter Dev** in the app and Mail extension. `./MacApp/install-dev.sh` builds and stages it at `/Applications/Mail-Filter Dev.app`, preserving a previous staged copy under ignored `outputs/development/`. Its app/extension identifiers and App Group differ from Store, so settings, activity and recovery records remain separate. It never replaces `/Applications/Mail-Filter.app`, imports setup or enables an extension. The default `package.sh` and **Mail-Filter Dev Installer** scheme create `outputs/Mail-Filter Dev Installer.pkg`, installing the same isolated app in `/Applications`. The installer title and introduction include version and build. The legacy Local installer is explicitly named **Mail-Filter Direct Installer.pkg** and refuses to replace Store. Mail controls independent extension checkboxes; disable Store before enabling Dev, and reverse those choices afterward.

`Common.xcconfig` holds shared defaults; the five named configurations define signing, identifiers, storage and compilation conditions. Local preserves the installed direct app's identity and private settings path. DeveloperID preserves the direct release group. Development and Store use their separate sandboxed groups. BuildCheck disables signing and never launches an app.

Each named `.xcconfig` applies to all targets built with that configuration. Local and Development explicitly set `COPY_PHASE_STRIP = NO` (Xcode's **Strip Debug Symbols During Copy**) so embedding the already-signed Mail extension does not produce the "not stripping binary because it is signed" warning. Keep this override in the configuration files so project regeneration preserves it. Store and DeveloperID retain their distribution defaults; stripping the linked product is a separate setting.

Keep build-setting changes in these configuration files or the project generator so regeneration preserves them. Xcode's recommended compiler warnings are recorded in `Common.xcconfig`. Do not let a recommended-settings update replace Developer ID signing with an Apple Development identity. The Store configuration intentionally uses automatic development signing for its archive; export re-signs it for App Store distribution. The generator's `--check` compares project and scheme structure using macOS's built-in `plutil` and Python's XML parser; Xcode formatting, redundant file labels, encoding-scan and upgrade-version metadata do not count as build changes. Changes to targets, dependencies, signing settings and scheme actions still require reconciliation.

Copy `Signing.example.xcconfig` to the ignored `Signing.local.xcconfig` to set a private developer team for signed configurations. Local and BuildCheck do not use it. An existing file under the former Store directory belongs here now. Never commit certificates, profiles or personal signing overrides.

Native builds regenerate Word documentation. Direct packaging stages the native app, CLI and uninstaller, embeds engineering resources only in the staged direct app, and reseals the signature before verification. Store schemes exclude these engineering products.

## Dev self-mail testing

Only `Development.xcconfig` defines `MAIL_FILTER_DEV`. The signed Dev app exposes **Analyze and filter self-sent mail (Dev)**, defaulting to **ON** for new settings and older files without the key. An explicit saved OFF choice is preserved. ON permits classification and verified Junk actions for own-sender mail; OFF protects it without analysis. The UI explains both states and flags an unsaved change. **Save Settings** applies the switch to the Dev extension and read-only analysis. Production builds omit the saved field and bypass entry point, so an imported Dev setting cannot disable Store self-mail protection. Preview, recipient selection, body/identity checks, evidence and recovery remain active. See the developer guide for the fresh-message test procedure.

## Application icon

`MacApp/Resources/PoliticalAdFilter.icns` preserves the supplied icon package. The ten PNG slots in `Assets.xcassets/AppIcon.appiconset` are imported from that package and compiled by Xcode for the app and uninstaller across build configurations. The original ICNS is a source reference, not an extra runtime resource.

To unpack a replacement package, run `iconutil --convert iconset MacApp/Resources/PoliticalAdFilter.icns --output /tmp/Mail-Filter.iconset`, then update every PNG named in the catalog's `Contents.json`. Preserve supplied sizes; a slot missing from the package can reuse an image with the same pixel dimensions or be resized with `sips`. This package supplies eight slots: the 32-pixel image also fills `icon_32x32.png`, and a copy resized to 16 pixels fills `icon_16x16.png`. Keep the source package and catalog images together in source control. Builds use the checked-in catalog directly.

See [Developer Getting Started](../../docs/dev/getting-started.md) for building, testing and packaging; see [Store workflow](../Store/README.md) for signed archive/export steps.

The extension's display name in Mail includes the shared build number; its numeric marketing version is unchanged. The legacy direct installer requires Mail, Mail-Filter and its uninstaller to close before replacement. The Dev installer requires Mail and Mail-Filter Dev to close. A read-only preinstall guard also rejects a lingering production extension process, including during command-line installation. No installer script terminates apps or erases settings. See the developer guide for update qualification and startup diagnostics.
