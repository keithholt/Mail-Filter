# Mail Filter Architecture

Mail-Filter is a native macOS settings app and MailKit extension that analyzes incoming Apple Mail messages on-device and requests Junk actions for political solicitations. This guide explains how the code fits together, why the boundaries exist, and the invariants to preserve when changing it. It covers candidate build 27, including the unified Xcode build, separate Dev installation and Store distribution. Version 2.1.0 passed App Review; later changes require their own qualification and review.

This is a living design document. Update it when a subsystem or contract changes. Markdown is the source of truth; `architecture.docx` is generated by `docs/build-docx.py`. Developer setup and validation belong in `docs/dev/getting-started.md`. The root `README.md` describes the user-facing app, while `README-DEVELOPER.md` retains engineering CLI and timer instructions.

## 1 Product and process boundaries

The direct installer contains a settings app, an embedded MailKit extension, an engineering CLI, and a separate uninstaller. The Store payload contains only the settings app and extension. The settings window does not host the extension. Mail loads the extension in its own process and calls it as messages arrive. Closing Mail-Filter leaves that process independent; Mail must be running and the Mac awake for incoming processing.

```text
Mail-Filter settings app           Apple Mail
  account discovery                  received-message callback
  saved policy and controls                   |
           |                          Mail-Filter.appex
           |                            MIME extraction
           |                            input guards
           |                            serial admission
           |                            Foundation Models
           |                            evidence validation
           +---- private shared files -- final action gate
                                              |
                                      request moveToJunk
                                              |
                                      Mail applies the action
```

Apple Events are used by the host for account discovery and explicit selected-email diagnostics. Incoming filtering uses MailKit, not AppleScript or the CLI. Mail-Filter requests an action; it does not receive a confirmation that Mail completed a move. The activity count therefore means **Junk actions requested**, not confirmed mailbox changes.

The engineering CLI is a separate executable with its own account file, prompt files and state. It shares the model interface and evidence verifier, but reads and moves messages through Apple Mail scripting. Its timer baseline remains tagged `v1.0.0`. There is no timer fallback in the native extension, and the retired Probe app is not built.

## 2 Source map

The root `Mail-Filter.xcodeproj` defines the native app, MailKit extension, engineering CLI and uninstaller. `MacApp/generate-project.py` owns their source lists and reproducibly generates the project and shared schemes. Local, DeveloperID, BuildCheck, Development and Store configurations select signing, identifiers, storage, entitlements and `APP_STORE` conditions for the same app/extension targets. Shared Swift files compile into each executable that needs them; they are not a separately packaged framework. The root Swift package additionally builds the standalone CLI and its tests.

`MacApp/build.sh` and `store-build.sh` invoke these Xcode targets. The local installer aggregate depends on the app, CLI and uninstaller; the host itself depends on its extension. Its packaging phase consumes the built products without recursively compiling them. `prepare-direct-products.py` stages copies and embeds the separately built CLI and generic resources, then reseals the staged app. `package.sh` builds the installer from that verified staging area. Store schemes exclude the CLI, uninstaller and packaging helper from their target graph and payload.

Every native product depends on the documentation aggregate, which declares Markdown inputs and Word outputs and runs within Xcode's build-script sandbox. Only the installer packaging helper disables that script sandbox to write repo outputs and the Desktop shortcut. Runtime App Sandbox is a separate entitlement: the Local/DeveloperID host is unsandboxed, the Store host is sandboxed, and every MailKit extension is sandboxed. The Local extension retains its narrowly scoped home-directory storage exception; Store variants use only their provisioned group. These settings live in `MacApp/Build/` and do not move or reset private user data.

## 3 Incoming processing flow

`NativeMessageHandler.decideAction` handles only messages in the received state. It requests `message-id`, `delivered-to` and `x-original-to` headers. A callback without raw data can return `invokeAgainWithBody`; `BodyRequestTracker` avoids repeatedly requesting the same identity while retaining a bounded recent set. If the body still cannot be obtained, the message stays in place with a diagnostic category.

When raw data is present, the handler decodes it, preserves the sender display name, and derives delivery recipients. Delivery headers take precedence over visible recipient addresses. It then passes immutable input into the main-actor classifier and eventually completes with either a Junk action or no action. Every branch must complete the callback once.

The classifier performs these stages in order:

1. Load valid private settings and stop if paused or not configured.
2. Protect own-sender mail, reject unselected recipients, and require meaningful body text, valid RFC identity and bounded headers.
3. Check persistent protection before doing model work.
4. Hash the policy revision and message payload for scheduler admission.
5. Generate a label within the retry/deadline budget and verify any positive against source evidence when keywords are configured.
6. Recheck the current policy under the store lock, reserve protection if applying, and return the action to Mail.

**Account selection is an approximation in MailKit.** The handler does not receive the CLI's exact Mail account ID. It routes by delivered-to/original-to headers or visible recipients, so aliases, forwarding, Bcc, shared addresses and delivery into several accounts can be ambiguous. The UI selects stable account IDs, then saves their recipient addresses. All addresses from the collected inventory protect own-sender mail, including accounts not selected for filtering. Refresh the inventory when accounts or aliases change.

Only the signed Development configuration defines `MAIL_FILTER_DEV`. It adds the opt-in `filterOwnMailForTesting` field to NativeSettings, a self-mail switch in the Filtering page and a dedicated development routing entry point. The default is off, including when older settings lack the optional field. When on, incoming and read-only analysis omit only the own-sender exclusion. Selected recipients, meaningful body, identity/header limits, Preview, evidence and recovery still apply. Saving the switch creates a new revision, invalidating an in-flight result. Store and Local compile neither the field nor the bypass entry point; importing a Dev archive into production ignores that key. The CLI retains its existing own-sender guard.

Account refresh treats a successful Mail inventory as authoritative. `NativeAccount.refreshed` replaces the displayed list, retaining checked and unchecked choices by stable ID even when names or aliases change. Address matching supports transition from manual setup to discovered accounts. Removed accounts and missing manual aliases are not recreated from saved own-sender addresses. Discovery failure leaves the current list intact. Refresh changes the UI draft; **Save Settings** rebuilds recipient and own-sender addresses from that draft without clearing restored-message protection.

## 4 MIME extraction and input limits

The decoder accepts plain text and HTML and handles common multipart structures and transfer encodings. For alternatives it prefers a readable nonempty plain-text representation, then another readable representation. A malformed optional alternative can be skipped when a valid sibling exists; global resource limits remain fatal. Related messages use their root document, and signed messages use the first content part.

Attachments, embedded messages, images and other nontext parts do not contribute to classification. HTML conversion does not open URLs or load images. An unsupported charset, malformed structure or exceeded resource limit produces a failure category and no action.

| Limit | Current value | Effect |
|---|---|---|
| Raw message | 2 MiB | Larger source is rejected. |
| Header block per entity | 64 KiB | Oversized or malformed headers are rejected. |
| MIME nesting | Depth below 8 | Excess nesting is rejected. |
| MIME parts | 128 | Excess parts are rejected. |
| Decoded text bytes | 256 KiB | Excess decoded text is rejected. |
| Classified body | First 6,000 Swift characters | Remainder is excluded; truncation is reported. |
| Subject and sender | 500 characters each | Oversized headers are skipped. |

The 6,000-character limit is an application policy, not Apple's token limit. Truncation alone does not prevent a positive result. Classification and evidence must use the same excerpt; neither may use a political footer outside those first 6,000 characters. Whitespace, control characters and invisible formatting alone do not make a meaningful body.

## 5 Model contract and evidence

`PoliticalModel` constructs a `SystemLanguageModel` request using permissive content transformations and asks for exactly one string label: `political` or `not-political`. Saved policy is included in session instructions; email fields are JSON-encoded data in the prompt. The model receives subject, sender and body, plus context anchors for split sections. Account inventory, recovery identities and owned-address lists are excluded from the model payload, although addresses naturally present in email content remain part of that content.

**Keep production generation on the String overload.** Apple's permissive transformation mode applies to string responses. Adding `schema:` or `generating:` causes guided generation to use the default guardrails. Build 11 introduced that regression; build 12 restored string generation. See [Apple safety documentation](https://developer.apple.com/documentation/foundationmodels/improving-the-safety-of-generative-model-output). Permissive mode can still produce a textual refusal. The parser accepts only a whole label with limited harmless formatting, not a label found inside explanatory prose. Refusals and invalid labels leave the message untouched.

Model context is budgeted separately from character limits. On macOS 26.4 or later, actual token counts include instructions and the complete prompt. The planner reserves 256 output tokens and 512 framing tokens. Build 24 starts with at most 3,000 characters per section; retries cap sections at 1,500 characters. Earlier systems estimate from UTF-8 length and start at 1,500. The first 6,000 body characters remain eligible. Oversized requests are split with 128-character overlap; each split prompt carries opening and closing context from the same excerpt. There are at most 12 sections. Each section gets a fresh session. A positive may finish early; a negative requires every section to complete successfully.

Whole-label parsing tolerates boundary whitespace, byte-order/directional marks, whitespace inside paired double quotes and CRLF text fences. It does not strip characters from inside words or accept labels embedded in explanations, JSON or conflicting answers. These are formatting corrections; configured political evidence verification and restored-message protection still apply.

The bundled policy no longer asks for a short explanation that conflicts with the label contract. Host startup recognizes the two prior standard-policy digests and upgrades only untouched policies; custom prompts and empty keyword lists are preserved.

With a populated keyword list, the model label does not authorize a move by itself. `validatePoliticalEvidence` requires a positive and a configured verification term in the subject or classified body. It recovers an actual subject, sentence or bounded source window; it does not use the sender or unseen remainder as evidence. A term match never promotes a negative result. Broad terms such as donation, candidate and campaign support verification only after the model identifies political purpose; the saved policy distinguishes political appeals from ordinary marketing, charity, medical information and personal correspondence.

An explicitly empty keyword list disables this secondary verification in both native filtering and the CLI. It does not turn a negative or invalid response into a positive. Empty lists remain valid through save/load, setup migration and standard-list upgrades. Restore defaults loads the bundled prompt and keyword text into the two editors; Save Settings applies them with a new revision, preserving accounts, mode, pause and recovery data.

The current interface returns an application-supplied reason describing the label, not a generated rationale. The verified quote and original processing stages are the concrete diagnostic evidence. Keep model accuracy, valid output format, evidence acceptance and Mail action delivery as separate questions.

## 6 Concurrency and retry budgets

Settings/UI state, model orchestration and the incoming scheduler use `MainActor`. Async inference yields while awaiting the framework. MailKit callback and body-request bookkeeping can run outside that actor; the tracker protects its set with `NSLock`. Cross-process file coordination uses file locks, not actor isolation. Unified-log collection runs on a detached utility task with a nonblocking pipe, so a stalled log command does not freeze the UI.

`InspectionScheduler` permits one active job plus 16 waiting jobs. Its fingerprint includes settings revision and message data. Pending duplicates and up to 1,024 recent completed fingerprints are suppressed. A job that attempted classification and exhausted its budget, or failed permanently, becomes terminal for that exact fingerprint. A later settings revision, changed input, cache eviction or new extension process can admit it again. This cache is not persistent restored-message protection.

| Budget | Current value |
|---|---|
| Classification attempts | 3 total, including the first |
| Per-attempt deadline | 20 seconds |
| Overall classification deadline | 60 seconds |
| Backoff after failed attempts | 1 second, then 2 seconds |
| Body-request identities retained | 1,024 |
| Completed classification fingerprints retained | 1,024 |

The 60-second classification deadline begins after scheduler admission; it does not bound time waiting in the queue. Transient generation failures, malformed labels and timeouts can retry. Context-limit retries reduce section size to avoid repeating the same oversized request. Valid negatives, refusals, unsupported requests and rejected evidence are terminal. Model unavailability is checked before an attempt and is not cached as an attempted classification failure.

`AnalysisDeadline` returns even if an underlying operation ignores cancellation. Late results cannot reach the action gate. Build 26 uses a strict one-shot Dispatch timer with 10 ms requested leeway; the earlier background `asyncAfter` timer returned at about 63 seconds in a 60-second qualification. This tightens timer scheduling without increasing the configured limits. Scheduling remains best effort, not a hard real-time guarantee.

`ModelExecutionGate` in `PoliticalModel.swift` serializes actual SDK awaits within a process, including token counting. A canceled or timed-out caller cannot release an active SDK slot until the call returns. Canceled waiters leave promptly, and remaining waiters resume in order. Production `Engine.system` always uses the shared gate. Some fault tests deliberately inject an ungated engine to reproduce the former overlap. The final action gate still discards every late result.

This distinction matters: `InspectionScheduler` serializes logical message jobs, while `ModelExecutionGate` owns the longer-lived SDK call. The full-duration qualification reproduced two concurrent unreturned calls under the former transport and one with the corrected adapter. Separate processes still have separate gates, and an SDK return cannot establish that Apple’s underlying service has stopped physical inference. No test claims machine-wide model exclusivity or automatic recovery from an SDK call that never returns.

Queued job cancellation now removes the waiter promptly without running its operation. MailKit action completions remain pending through queueing and analysis; the callback thread itself returns promptly. This is not a guarantee that Mail’s download pipeline is unaffected. Queue residence has no separate deadline, and there is no durable retry queue or guaranteed later MailKit callback. These delivery and backlog limits require explicit qualification before proposing a broader queue redesign.

## 7 Private state and the final action gate

Host, extension and uninstaller resolve storage from their bundle metadata. Local test builds use `~/Library/Application Support/Mail-Filter Local/` with a narrowly scoped sandbox exception. Release builds use the team-prefixed App Group container and its `Mail-Filter` subdirectory. Failure to obtain a release container stops filtering; it must not fall back to local storage.

| File | Purpose | Failure behavior |
|---|---|---|
| `settings.json` | Account inventory, selected IDs, pause state, policy and revision. | Invalid or unsupported settings stop filtering without replacing the file. |
| `activity.json` | Counts and at most 500 fixed-category events. | Read/write failure is reported separately from move protection. |
| `junk-protection.json` | Persistent hashed identities reserved for Junk actions. | Invalid, busy, inaccessible or full state prevents a new action. |
| Lock files | Nonblocking cross-process exclusion for settings and protection. | Contention fails safely instead of waiting indefinitely. |

Settings and activity use schema version 1; the embedded filtering configuration uses schema version 2. Writes are atomic and owner-readable/writable; newly created private directories use mode 0700. Activity is bounded to 1 MiB on both write and read; when rich metrics exceed that byte budget, oldest events are evicted before saving without changing aggregate counters or the retained extension-start identity; settings allow 16 MiB for imported recovery digests. Protection accepts at most 100,000 digests within a 16 MiB input bound. Settings and protection have distinct locks; preserve their lock order and do not hold a lock across model generation.

`SetupArchive` is a versioned private export with full native settings and native recovery digests. Import validates policy against UI inventory and selection, merges destination protection and inherited CLI identities, and writes a destination backup. Incoming digests commit in the same atomic settings replacement through optional `importedProtection`. Optional `activationRequired` blocks both classifier admission and the final action gate until confirmation. Confirmation changes the revision and preserves pause. These additive settings fields remain readable from older schema-1 files; older binaries do not implement the new migration gate, so do not downgrade a migrated installation without preserving its recovery data.

The UI imports one archive or an explicitly selected legacy folder containing both siblings. It never assumes a selected settings file authorizes an adjacent protection file. Saving settings no longer probes CLI state or retired containers implicitly. Manual account groups use local IDs and preserve the separate own-address and selected-recipient sets.

Before apply, `SharedStore.finish` reloads settings under lock and requires the original revision, filtering still enabled, a positive with evidence when keywords are configured, and no previous protection. Preview returns `previewPolitical` without reserving identity. Apply atomically reserves protection before returning `junkRequested`. A save or pause during inference invalidates the old result through its revision.

The protection key is a SHA-256 digest of a versioned namespace and canonical RFC Message-ID, independent of mailbox and account. Mail's numeric ID is not the recovery identity. A message restored from Junk remains protected across restarts and policy changes. Reservation is conservative: failed or unconfirmed moves also remain protected. There is no automatic deletion or age-based eviction of protection records. Migration can import compatible CLI identities and merge native protection; preserve previous data until verified.

Reinstallation replaces application bundles and preserves compatible private state. Standard prompt/list upgrades only recognize unchanged shipped versions; custom policies are retained. A changed storage mode or signing group needs explicit migration. The uninstaller removes only validated installed products and its exact owned PATH entry; private data is preserved unless the user explicitly chooses erasure.

## 8 Diagnostics and privacy

Ordinary activity records contain stages, categories, timestamps, attempt numbers, safe error domain/code and an optional 12-character identity digest. They exclude subjects, addresses, bodies, model response text and generated explanations. The report displays the latest 30 activity events, while activity retains up to 500. Supplemental JSON-lines files rotate under the same store lock at one MiB, with at most three files. Reports filter to seven days and expired files are pruned on a later write. Rotation never expires recovery protection. Log-write failure leaves the saved activity usable.

Build 24 adds optional, validated numeric request measurements to the same activity schema: section and excerpt lengths, section limits, instruction/prompt token counts, model context size, output limit, response characters/UTF-8 bytes and elapsed milliseconds. macOS 27 also supplies actual input, output and reasoning token usage. Earlier systems leave usage unavailable and label estimated input counts explicitly. A measured output count reaching the configured limit is evidence to investigate truncation, not proof of its cause. Smaller starting sections and increased output headroom are intended to mitigate first-attempt failures; synthetic success does not establish that the affected Mac's original failure is fixed.

Empty or whitespace-only output is `modelEmptyResponse`; nonempty text outside the two-label contract remains `invalidModelResponse`; refusals remain distinct. Request-start and request-finish events make unfinished generations visible without saving their text. Physical memory, observed Dispatch memory-pressure notifications and thermal state supply system context. Pressure is `unknown` until a notification arrives; it is not inferred from installed RAM. Shared activity stores only whitelisted categories and bounded numeric measurements. These fields are additive; existing settings and recovery records are unchanged.

Body-ready callbacks include their monotonic wait time when the same handler recorded the request. Support reports list requests older than 30 seconds that lack a newer matching body-ready event in retained history. That is an observation about bounded history, not a declaration of a Mail failure. It adds no timer, mailbox polling or automatic reprocessing. Explicit selected-email analysis includes per-attempt measurements and a bounded Unicode-scalar rendering of a rejected reply, so invisible characters can be inspected privately. Ordinary reports never contain that rendering or the reply itself.

The Store build reads this private history and exports reports through a Save panel; it compiles out the system-log collector with `APP_STORE`. The direct developer build may also collect `org.mail-filter.app` logs, keeping a 32,000-byte tail and stopping after ten seconds. A missing event is not proof that Mail did not invoke the handler: records may be older than retention or storage may have failed. User-opened email files use the same MIME/model/verifier path and can be exported separately; recipient matching is diagnostic and never grants a mailbox action.

Selected-email analysis is separate and read-only. It obtains one message's RFC source through AppleScript, decodes with the same MIME extractor, and uses the current saved policy and model interface. Its retained automatic history explains original processing; its current label is a new test. It does not request Junk or reserve protection. Exact routing guards and original settings can differ from the automatic path, so a current positive is not proof of an earlier positive.

An explicit selected-email export includes full RFC source as base64, extracted excerpt or decoding error, current policy, opaque key, retained history and a matching cached analysis. Cached analysis must match message identity and policy revision. The export can contain private content and is written with mode 0600. It excludes the account inventory but is not a sanitized public artifact. Keep reports and extracted emails outside this public repository; ignore patterns are only a secondary defense.

Build 27 keeps an owner-only `model-failures.json` cache of automatic rejected replies, including failures followed by successful retries. It stores exact UTF-8 bytes (up to 8 KiB), full-reply SHA-256, truncation, policy revision, request ID, instruction/prompt fingerprints and metrics. Limits are 32 records and 512 KiB. Exports exclude records older than seven days; subsequent writes prune them. Corruption can be recovered without changing settings or protection. Capture failure cannot block classification. Application-data removal deletes the cache.

These replies may contain private email text and appear only in explicit matching-email exports, which indicate cache availability. Ordinary activity, Console and application reports exclude them. Current environment metadata is labeled as current; per-request variant and reasoning capability describe the automatic call. Fingerprints cannot reconstruct an earlier custom policy. Queue admission duration, completed model-slot wait and ownership at failures distinguish backlog from outstanding SDK awaits. They do not observe Apple's internal cleanup or coordinate processes.

`ModelProbe.swift` is an engineering experiment, not another GUI or extension. The supported-path comparison reads exports and synthetic controls without accessing Mail, moving messages or changing settings. Historical guided/tagging trials remain comparisons and must not replace the production contract without actual model validation.

The request-budget comparison independently varies maximum section size (6,000 or 3,000 characters) and output budget (64 or 256 tokens), retaining request measurements for successes and failures. It includes short and long synthetic receipt/campaign controls. This is an experiment; it neither changes production settings nor establishes that a particular hardware memory size caused a failure.

The injected test transport implements the same PoliticalModel.Engine contract as the system adapter. `ModelGateChecks.swift` adds 200 cancellation/handoff races and FIFO/error/tokenization checks; the accelerated timing suite is part of the normal native tests. `qualify-timing.sh --full` separately uses actual 20-/60-second budgets and 1-/2-second retry delays, with real timers and scripted SDK stalls. `probe-model-queue.sh` uses the actual model, fictional dense-link messages and temporary NativeClassifier state to compare queued and paced blocks and recreate the historical unbudgeted context error. See the timing and queue investigation for results and limits.

 Production selects fresh Apple string sessions; developer tests select scripted replies and errors. Both paths use identical token planning, section coverage, parser, numeric metrics and cancellation checks. NativeClassifier tests additionally inject a temporary store and short deadlines while retaining the real retry, scheduler and final protection gate. Fault scripts are test sources, excluded from shipped targets; there is no runtime fault setting in the Store app.

## 9 Build boundaries and change rules

The root Xcode project compiles the host, extension and uninstaller in Swift 5 language mode for arm64 macOS 26 and the CLI in Swift 6 mode. It processes the channel-specific metadata and entitlements, embeds the extension and default resources, and signs native products. Direct packaging adds engineering resources only to staged copies and reseals the host. The Swift package requires tools version 6.2. Store configurations select sandboxed host/extension entitlements, user-selected file access and a Mail-targeted host automation exception. Development displays Mail-Filter Dev and uses org.mail-filter.development with group.org.mail-filter.development.shared; Store uses org.mail-filter.app with group.org.mail-filter.shared. The explicit Mail-Filter Dev scheme and install-dev.sh stage the signed Dev app alongside Store without importing or sharing settings. Legacy Local packages still use the production bundle identity and must not replace a working Store app for routine testing. Full Xcode supplies the SDK; no external library dependency is introduced.

`store-build.sh check` produces an unsigned archive with development identities and checks payload exclusions and privacy manifests. Signed Development uses the test Mac as its destination and permits automatic provisioning/device registration. The Store archive uses automatic development signing with production identities; export re-signs it for App Store distribution. The verifier's explicit archive mode checks provisioned capabilities, while final distribution verification additionally requires the appropriate signing identity and distribution profile without debugging permission. No Store build command installs, enables or submits a filtering extension. Xcode records build products with Launch Services; development identities keep compile checks distinct from production.

`Store/verify-export.py` checks the exported installer signature, expands the package into a temporary directory, runs strict distribution validation on its single app and embedded extension, rejects custom installer scripts, and checks that app and installer signing teams match. Expanding a package does not execute or install its payload. An archive-stage success cannot bypass this final export check.

Preserve these invariants when editing:

- A model positive, source evidence when keywords are configured, unchanged settings and persistent reservation are required before requesting Junk.
- Production own-sender, empty-body and restored-message protection run before model work. Only the opt-in Dev switch bypasses own-sender exclusion; its compile flag must never reach Store. Never use verification words as an independent classifier.
- Native filtering, selected-email analysis and CLI share `PoliticalModel`; their routing, state and action paths remain distinct.
- Keep production string generation and bounded token planning. Do not add a guided schema as a formatting fix.
- Every callback completes once; queue, retry and storage failures leave the message in place. Do not claim Mail guarantees a retry.
- Keep ordinary diagnostics free of email content. Private reproductions never become committed fixtures.
- Update the project generator when adding shared files, verify channel build graphs, and keep native and CLI default resources aligned.
